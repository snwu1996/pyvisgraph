# Benchmark obstacle maps

Twenty deterministic KML obstacle maps used by
`examples/profile_shortest_path.py` to compare A* against Dijkstra on the
visibility graph. All maps are generated by
`examples/generate_benchmark_kml.py` (fixed seed per map, so the files are
reproducible fixtures) inside a ~0.5° x 0.5° extent near 6°E / 51°N, the
same area as the other example KMLs.

Regenerate the maps and rerun the report with:

```bash
poetry run python examples/generate_benchmark_kml.py
poetry run python examples/profile_shortest_path.py
```

## The maps

### map_01 – map_10: disjoint obstacles

Jittered n-gons (4–8 vertices, radii jittered per vertex) placed on
distinct cells of a grid, so the shapes never touch each other. The ladder
increases the obstacle count: 3, 6, 12, 20, 30, 45, 60, 80, 105, 130.

A few of the generated rings are self-intersecting "bowties"
(map_04–06, map_08–10); the viewer loader repairs them with shapely's
`make_valid`, which splits a bowtie into its lobes — that is why the
loaded polygon count can slightly exceed the authored count (e.g. map_10:
130 authored shapes → 134 polygons).

### map_11 – map_20: overlapping obstacles

The same complexity ladder (3 … 130 shapes), but the shapes are grouped
into clusters of 2–3 that overlap each other, one cluster per grid cell.
These exercise the loader's dissolve step: pyvisgraph's rotational sweep
assumes polygon edges never cross, so `load_polygons` merges each cluster
into a single obstacle with `unary_union` before the graph is built. The
dissolved obstacle count is therefore well below the authored shape count:

| map    | authored shapes | dissolved obstacles |
|--------|----------------:|--------------------:|
| map_11 |               3 |                   2 |
| map_12 |               6 |                   2 |
| map_13 |              12 |                   6 |
| map_14 |              20 |                   8 |
| map_15 |              30 |                  17 |
| map_16 |              45 |                  19 |
| map_17 |              60 |                  26 |
| map_18 |              80 |                  35 |
| map_19 |             105 |                  48 |
| map_20 |             130 |                  55 |

(Loaded counts can again differ slightly where `make_valid` splits an
invalid ring.)

## Benchmark report

`profile_shortest_path.py` loads each map, builds its visibility graph
once, then times 20 seeded-random origin/destination shortest-path queries
(best of 3 runs each) with both algorithms and verifies both return paths
of equal length. `*_ms` columns are the mean per-query time; `*_nodes` are
the mean nodes settled by the search.

Observations:

- A*'s advantage grows with map size, from ~1.1x on the tiny maps to
  ~2–2.4x on the largest, because its Euclidean heuristic keeps the search
  focused: on map_20 it settles ~10 nodes per query where Dijkstra settles
  ~370.
- The overlapping maps (11–20) end up with fewer but larger obstacles
  after dissolving — e.g. map_20 has 55 obstacles carrying 756 vertices
  versus map_10's 134 obstacles with 774 — so query times land close to
  their disjoint counterparts while the merged outlines produce slightly
  denser visibility graphs (more mutually visible vertices per obstacle).
- Query time tracks the visibility-edge count roughly linearly for
  Dijkstra; A* grows noticeably slower than that.
